How STT & TTS latency is calculated

Two numbers, both measured server-side in the Pipecat pipeline using time.perf_counter() — monotonic, high-resolution, the correct clock for durations in Python. Browser clocks are never involved.

STT latency "user speaking → transcript ready for the LLM"

Timed between two frames flowing through the pipeline, both observed by UserTranscriptBridge, which sits right after the STT service:

  • Start: UserStartedSpeakingFrame — Pipecat's VAD has decided the user is actually talking.
  • Stop: the first non-empty final TranscriptionFrame — the transcript about to be handed to the LLM.
latency_ms = (t_stop - t_start) * 1000
Includes Network round-trip to the STT provider, provider compute, endpointing (the provider deciding the user is done).
Excludes The mic-to-server upload of the audio — start fires on audio that's already arrived.

TTS latency "text handed to provider → first audio out" (TTFB)

  • Start: inside TtsUsageMeterMixin.run_tts(text, context_id) — the exact seam where Pipecat hands text to the provider (a Deepgram Speak message or an ElevenLabs context text). Only stamped if a timer isn't already running, so multi-chunk streamed LLM text doesn't reset the clock.
  • Stop: the first OutputAudioRawFrame observed downstream of the TTS service, caught by a small TtsLatencyBridge FrameProcessor placed right after tts in the pipeline. 
latency_ms = (t_stop - t_start) * 1000

This is TTFB — first byte back from the provider. And because we stream raw linear16 PCM to the browser (no WAV / MP3 / Ogg container wrapping), the first byte is an audible audio sample. So TTFB and TTFA (time-to-first-audio) coincide — the number is honest, unlike TTFB on container-wrapped formats where the first bytes are just headers.

Includes Network round-trip to the TTS provider and provider synthesis time up to the first audio chunk.
Excludes Browser-side jitter buffer and audio decode.

Aggregation per-turn samples → session numbers

Each STT and TTS service holds a per-instance list of samples (one entry per utterance for STT; one per run_tts invocation for TTS). Each per-turn measurement is also emitted as a trace event (latency.stt.turn / latency.tts.turn) with {provider, model, latency_ms, turn_index}.

At session close, _summarize_latency() collapses the samples into:

  • median — plain nearest-rank median.
  • p95 — nearest-rank: ordered[ceil(0.95 * n) - 1]. Stable at small n, which matters for short calls with only a handful of turns.

Result: {provider, model, count, median_ms, p95_ms} for STT and for TTS, for the provider actually configured on the agent — not a cross-provider fan-out.

SttEvaluationSession.finalize() writes both under session_stt_latency_ms and session_tts_latency_ms in the session.summary line of metrics.jsonl. The /audio-evaluations/... route reads them back, and AudioView renders four cards: STT median / p95 and TTS median / p95, each sub-labelled with the provider actually used.

The 30-second version what to say when someone asks

For every turn we record two timestamps on the server with a monotonic clock. STT: from VAD-says-user-started-speaking to first final transcript. TTS: from text-handed-to-provider to first audio chunk out — TTFB, which equals TTFA here because we stream raw PCM, not container-wrapped audio. We collect per-turn samples and report median and p95 for the provider actually used. All server-side, so browser jitter doesn't pollute the numbers.
